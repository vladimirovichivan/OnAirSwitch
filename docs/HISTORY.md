# История решений (перенесено из Legacy)

Ниже — решения, определившие текущее поведение. Полные тексты с обоснованиями и
датами проверок — в `D:\Legacy\docs\decisions.md` (D-54…D-64). D-65 принято
уже в этом проекте; Legacy по лампе больше не развивается (D-64).

| ID | Решение | Суть |
|---|---|---|
| D-54 | Наблюдатель встреч | Определять встречу локально по видимым окнам; события в журнал; устройствами не управлять |
| D-55 | Розетка по событиям | Локальный протокол Tuya (ключи из облака один раз), сверка «желаемое/фактическое», отдельный исполнитель, dry-run по умолчанию |
| D-56 | Порог старта | Старт и завершение — 3 замера (≈6 с); признак Zoom — окно, а не тема |
| D-57 | Заголовки окон в логе | На время апробации пишутся заголовки видимых окон (до 6, до 120 символов) |
| D-58 | Только окно | Аудиосессия не признак встречи: окно настроек Толка давало ложную встречу и лампу, горящую ночью |
| D-59 | Настройки и плавающее окно | Настройки Телемоста — служебное окно; у Zoom добавлены классы свёрнутого плавающего окна |
| D-60 | «Звонок» Телемоста | Это сама встреча, а не лобби: окно ожидания для Телемоста не определяется |
| D-61 | Ручное управление | Файл намерения `control.json`, CLI и иконка в трее; единственный клиент устройства — исполнитель |
| D-62 | Тиражирование | Отдавать другим людям как упакованное приложение, а не копию скриптов |
| D-63 | Форма поставки | Снимок рабочей схемы: эмбеддированный Python + Inno Setup, без переписывания кода; три процесса, один автозапуск, открытый `tuya_plug.json`, адрес вручную и UDP-поиском |
| D-64 | Источник истины | Основной код лампы — `D:\onair-lamp`; Legacy по лампе больше не развивается, архивом не считается |
| D-65 | Основная ветка и ветка поставки | Разработка — в `main` проекта на GitHub; версия для передачи другим — ветка `Portable`, которая следует за `main`; портативные сборки — zip |

  исполнитель и трей из `D:\onair-lamp`;

- ручной режим из трея: включение на срок, затем возврат `auto` и выключение.

Замечания, найденные при запуске:

## Автономность: проверка и поиск розетки (16.11.2026)

Фаза 2 плана, без изменения семантики определения встреч:

- `tuya_setup.py --verify` — поиск адреса, чтение DP, переключение с
  подтверждением и возврат исходного состояния; во время встречи отказывается
  работать без `--force`;
- `tuya_discovery.py` — поиск по `dev_id`: скан `tinytuya.scanner.devices(...)`
  и резервное пассивное прослушивание UDP 6666/6667/7000; ключи не используются;
- исполнитель при молчании адреса один раз ищет устройство (не чаще раза в
  10 минут) и пишет `address rediscovered: <старый> -> <новый>`; конфиг не
  перезаписывается;
- при старте исполнитель пишет версию из `app\build.json`, без файла — `build dev`.

Проверено на реальном устройстве: `--verify` переключил и вернул состояние;
подмена адреса на недостижимый → `address rediscovered` и успешное чтение;
dry-run в изолированном процессе устройство не опрашивает.

## Сборка поставки и установщик (16.11.2026)

Фаза 3 плана. Компиляции кода нет: копируются `.py`/`.ps1`, рядом лежит
embeddable-Python и `vendor`.

- `packaging\build.ps1` скачивает `python-3.12.10-embed-amd64.zip`, ставит
  зависимости в `build\vendor`, проверяет импорты в готовой раскладке, рисует
  `onair.ico`, собирает портативную папку/zip и установщик, пишет
  `build\SHA256SUMS.txt`;
- в `python312._pth` добавлена строка `..\app\scripts\meetings`: embeddable-Python
  не добавляет каталог скрипта сам, иначе не находятся `plug_control` и
  `tuya_discovery`;
- установлен Inno Setup 7.1.1 per-user (`%LOCALAPPDATA%\Programs\Inno Setup 7`);
  `build.ps1` ищет 7, затем 6;
- `tools\report_support.py` и `packaging\report.cmd` собирают архив для поддержки
  на рабочем столе: журналы и состояния + `info.txt` без `local_key` и `dev_id`;
- ярлыки лежат в отдельной папке «OnAir Lamp» в меню Пуск (пять штук), а не в
  корне меню;
- артефакты: `build\OnAirLamp-1.0.0-win64.zip`, `build\OnAirLamp-Setup-1.0.0.exe`.

Проверено на этом ПК:

- портативная копия в отдельном каталоге отработала встречи в Толке и Zoom без
  участия `D:\onair-lamp`;
- установка `/VERYSILENT`: приложение в `%LOCALAPPDATA%\Programs\OnAirLamp`,
  ярлыки, автозапуск `HKCU\…\Run`, запуск и управление розеткой;
- повторная установка сохраняет `local_key` и журналы;
- удаление убирает автозапуск и ярлыки; при обычном удалении задаётся вопрос
  «удалить сохранённые настройки подключения к розетке?» (по умолчанию — нет),
  тихое удаление их сохраняет, `/DELETEAPPSETTINGS` удаляет;
- архив поддержки не содержит значений `local_key` и `dev_id` (проверено
  поиском по содержимому zip).

## Первый запуск без настройки (16.11.2026)

После установки трей показывал «нет данных», а кнопки управления не работали:
исполнитель завершался, если `app\secrets\tuya_plug.json` ещё не было, — а он
запускается раньше мастера настройки.

Исправлено:

- `plug_executor.py` без конфигурации не выходит: публикует
  `plug_state.json` с `configured: false` и ждёт, проверяя файл каждые 3 с;
  когда мастер записал конфигурацию, подхватывает её без перезапуска;
- `tray_plug.py` различает «исполнитель не запущен» и «розетка не настроена»;
  во втором случае показывает пункт «Настроить розетку…», открывающий
  `setup.cmd` из папки установки;
- `setup.cmd` после успешной настройки вызывает `restart.ps1`: останавливает
  процессы именно этой копии (по пути в командной строке) и запускает
  `start.vbs` заново.

Проверено на установленной копии: без `tuya_plug.json` исполнитель остаётся
работать и пишет `configured:false`, трей показывает «розетка не настроена»;
после возврата конфигурации `restart.ps1` перезапускает три процесса, статус
становится `configured:true`, розетка читается и управляется.

## Исправление Zoom 7.1 (16.11.2026)

Отдельного решения нет — исправление зафиксировано в `D:\Legacy\docs\current_state.md`
§3.21 (коммит `94b55af`).

- Симптом: лампа не включилась на встрече Zoom; `events.log` — `microphone on
  (outside meeting)`, `state.json` — `meeting: false`.
- Причина: в Zoom 7.1.9.48550 окно встречи называется `Zoom Meeting 40-Minutes`
  (суффикс — пометка лимита бесплатного тарифа, предположение), а шаблоны
  заголовков были привязаны к концу строки (`^zoom meeting$`). Класс
  `ConfMultiTabContentWndClass` в списке классов отсутствует.
- Исправление: якоря `$` заменены на `\b` в шаблонах `^zoom meeting\b` и
  `\s-\szoom meeting\b`. Класс `ConfMultiTabContentWndClass` намеренно не добавлен:
  не проверено, что он не встречается вне встречи.
- Проверено: `-Apps zoom -Once` → `state=meeting`; после перезапуска наблюдателя
  записано `meeting STARTED … "Zoom Meeting 40-Minutes"`, лампа включилась.
- Не проверено: сохраняется ли суффикс после встречи, поведение на платных
  тарифах Zoom, нет ли похожего суффикса у Толка и Телемоста.

## Один инструмент настройки вместо двух (17.11.2026)

Первый запуск без `secrets\tuya_plug.json` больше не требует находить в меню
Пуск два разных ярлыка:

- трей при старте сам предлагает мастер («Открыть мастер настройки?»); отказ
  ничего не блокирует, пункт «Настроить розетку…» остаётся в меню;
- `tuya_setup.py` после записи ключей сразу выполняет `--verify` (чтение,
  переключение и возврат состояния), поэтому «проверка пройдена» — часть
  мастера;
- повторный запуск `setup.cmd` на настроенной розетке не перезаписывает ключи,
  а предлагает выбрать проверку или повторную настройку (`--reconfigure`);
- в меню Пуск осталось четыре пункта: «OnAir Lamp», «Настройка и проверка
  OnAir Lamp», «Отчёт для поддержки», «Если не работает». `verify.cmd`
  сохранён в папке установки для поддержки, но отдельного ярлыка не имеет.
- «Выход» в трее теперь означает полное выключение: через `packaging\stop.ps1`
  завершаются трей, наблюдатель и исполнитель, а не только иконка.
- деинсталлятор перед удалением файлов запускает тот же `stop.ps1`, поэтому
  занятых процессов и «файл используется» больше нет.
- иконку трея заменили на нарисованную лампу с дугами Wi-Fi: жёлтая — включена,
  серая — выключена. Исходники были на чёрном фоне; фон снимает
  `packaging\key_icon.py` (свечение — по яркости с обратным умножением, корпус —
  по порогу с дилатацией), поэтому свечение осталось полупрозрачным, а цоколь
  непрозрачным. Версия не менялась.
- `build.ps1` вычищает `__pycache__` и `*.pyc` из `vendor` и раскладки, а
  проверку импортов выполняет с `PYTHONDONTWRITEBYTECODE`: в архив и установщик
  не попадает байткод машины сборки (zip похудел с 25,4 до 23,4 МБ).
- установщик больше не полагается на Restart Manager: скрытые `pythonw.exe` и
  наблюдатель не отвечают на запрос закрытия, и Inno показывал «не удалось
  автоматически закрыть приложения». Теперь `PrepareToInstall` в
  `OnAirLamp.iss` сам завершает процессы, у которых в командной строке путь
  установки (чужие Python не затрагиваются), затем ставит файлы. Деинсталлятор
  делает то же в начале удаления. `CloseApplications=no`.
- серая иконка трея без дуг Wi-Fi (новый экспорт на белом фоне); `key_icon.py`
  научился снимать и белый фон по обратной композиции, по краям нет белой каймы.
- на тёмной теме цоколь лампы поднимается по яркости: он почти чёрный и
  сливался с панелью задач (и у включённой, и у выключённой). Тема читается из
  `AppsUseLightTheme`; смена темы перерисовывает иконку сразу.
- собрана версия **1.0.1** (17.11.2026, `c5045b8`) из чистого `build\`:
  `build\OnAirLamp-Setup-1.0.1.exe` — `6eae7c0d…b70a25`,
  `build\OnAirLamp-1.0.1-win64.zip` — `a9aade80…af875d`.

## Иконка трея крупнее (17.11.2026)

Лампа в трее выглядела мельче соседних иконок: в кадре 64×64 она занимала
только 56 % ширины (≈9 px при отрисовке в 16 px), а у выключенной к тому же
попадал почти невидимый «призрак» над колбой.

- `_asset()` теперь оставляет только самую крупную связную фигуру — корпус
  лампы. Дуги Wi-Fi на 16–24 px превращались в бледную дымку, но забирали
  четверть высоты; корпус стал занимать ~65 % ширины и ~95 % высоты плитки.
- Порог обрезки считается по этой фигуре, поэтому призрак и ореол свечения
  больше не растягивают кадр; выключенная лампа стала того же размера, что и
  включённая.
- Связность ищется по уменьшенной копии альфы (шаг 4 px), одна иконка
  обрабатывается ≈0,1 с; маска возвращается в полный размер.
- Запасная отрисовка `_draw_lamp()` перерисована без дуг и с более крупной
  колбой, полосы паузы переставлены под новую геометрию.

## Удаление без следов (17.11.2026)

Пользователь удалил 1.0.1, выбрал удаление настроек и получил «Часть элементов
не удалось удалить. Вы можете удалить их самостоятельно». В папке установки
остались только журналы и состояние (`app\data\work\meetings`), программа,
ярлыки, автозапуск и настройки были удалены.

- Сообщение появлялось не из-за файлов: `[UninstallRun]` вызывал
  `{sys}\powershell.exe`, которого в System32 нет. `CreateProcess failed (2)`
  делал результат деинсталляции неуспешным (в логе — `Removed all? No`).
  Путь заменён на `{sys}\WindowsPowerShell\v1.0\powershell.exe` — тот же,
  что используют `start.vbs` и `KillLampProcesses`.
- В `[UninstallDelete]` добавлены рекурсивные записи для `app\data`,
  `app\scripts`, `python`, `vendor`, `tools`, `licenses`: удаляются журналы,
  состояние и `__pycache__`, которые приложение создаёт при работе.
  `app\secrets` в список не входит — его судьбу решает вопрос про настройки.
- Проверено вживую на 1.0.2: `/DELETEAPPSETTINGS` — `Removed all? Yes`,
  каталога установки не остаётся; тихое удаление с сохранением настроек —
  `Removed all? Yes`, остаётся только `app\secrets\tuya_plug.json`.
- Пункт «Настройка и проверка» открывал консоль с рваными командами
  (`'--reconfigure' is not recognized`, `The filename, directory name, or
  volume label syntax is incorrect`). Причина — `.cmd` в репозитории имели
  LF-переводы строк: cmd.exe путает разбор такого файла, особенно после
  `chcp 65001` и с кириллицей в строках. `setup.cmd`, `report.cmd`,
  `verify.cmd` и `scripts\restart-dev.cmd` переведены на CRLF, в
  `.gitattributes` добавлено `*.cmd text eol=crlf`. Проверены обе ветки

## Версия Windows в отчёте (17.11.2026)

Для аналитики в отчёте не хватало системы получателя: по журналам видно, что
сломалось, но не видно, на какой Windows это происходило.

- `tools\report_support.py` в `info.txt` пишет строку вида
  `ОС: Windows 11 IoT Enterprise LTSC 2024, 24H2, сборка 26100.1742, 64-bit`.
  Данные берутся из `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion`
  (`ProductName`, `DisplayVersion`, `CurrentBuildNumber`, `UBR`), разрядность —
  из `platform.architecture()`.
- `ProductName` в реестре Windows 11 иногда до сих пор равен «Windows 10».
  Если номер сборки ≥ 22000, версия в строке исправляется на Windows 11.
- Имени компьютера, пользователя и сетевых имён в отчёте нет; `local_key` и
  `dev_id` по-прежнему не включаются.
- Проверено на этой машине: в архиве появилась строка ОС с версией 24H2 и
  сборкой `26100.1742`; установленная сборка (портативный Python) выдаёт то же.
