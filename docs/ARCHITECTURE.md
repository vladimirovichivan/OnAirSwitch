# Архитектура

## 1. Что делает

Три независимых процесса, связанных файлами:

```
watch_meetings.ps1 ──> state.json ──┐
                                    ├──> plug_executor.py ──> розетка Tuya (TCP 6668, DP 1)
tray_plug.py / CLI ──> control.json ─┘            │
                                                 └──> plug_state.json ──> tray_plug.py
```

Почему именно так:

- **состояние, а не поток событий.** Исполнитель раз в 3 с сверяет желаемое и
  фактическое. Пропущенное событие, перезапуск процесса или обрыв сети
  исправляются следующим проходом; лампа не остаётся включённой «навсегда».
- **намерение отдельным файлом.** Принудительная команда, отправленная прямо в
  розетку, была бы отменена следующей сверкой (≤3 с). Поэтому «включить»,
  «выключить» и «снять автоматику» — это запись в `control.json`, а не команда
  устройству. Приоритет: `paused` > `on`/`off` > `state.json`.
- **единственный клиент устройства.** К розетке подключается только исполнитель:
  у устройства один слот соединения. Трей читает файлы и `local_key` не знает.
- **неизвестное состояние — не команда.** Если `state.json` устарел (порог 90 с)
  или отсутствует, исполнитель ничего не переключает: «нет данных» ≠ «встречи нет».

## 2. Компоненты

### `watch_meetings.ps1` — наблюдатель

- только чтение состояния Windows: видимые окна процессов, журнал доступа к
  камере и микрофону, аудиосессии (только для диагностики).
- встреча определяется **только окном**; аудиосессия признаком не является
  (иначе окно настроек Толка давало ложную встречу).
- профили: Толк (`ktalk.exe`), Zoom (`Zoom.exe`), Телемост (`YandexTelemost.exe`).
  Для Толка есть отдельное состояние «окно входа» (`Подключение к встрече`),
  оно даёт `meeting: false`. Шаблоны заголовков Zoom привязаны по границе слова
  (`\b`), а не к концу строки: Zoom 7.1 добавляет к заголовку суффикс
  (`Zoom Meeting 40-Minutes`).
- дебаунс: старт и завершение подтверждаются 3 замерами (≈6 с), интервал опроса 2 с.
- пишет `data\work\meetings\events.log` и атомарно `state.json`
  (`updated`, `meeting`, `apps.*.state`).
- второй экземпляр блокируется именованным mutex.

### `plug_executor.py` — исполнитель

- раз в 3 с: `control.json` → при необходимости `state.json` → желаемое состояние.
- читает DP 1, при расхождении отправляет команду и **проверяет результат
  повторным чтением**; до 3 попыток, затем пауза 60 с, чтобы не забивать журнал.
- по умолчанию dry-run, реальное управление — `--apply`.
- истечение срока режима возвращает `auto` и пишет об этом в журнал.
- публикует `plug_state.json` (фактическое состояние, режим, срок, ошибка) —
  его читает трей; heartbeat раз в 5 с.
- соединение не держит (`persistent=False`): команда нужна редко, а постоянный
  сокет занимает слот устройства.
- если настроенный адрес не отвечает, один раз (не чаще раза в 10 минут) ищет
  устройство по `dev_id` и продолжает с найденным адресом; в журнал пишется
  `address rediscovered: <старый> -> <новый>`. Конфиг не перезаписывается.
- при старте пишет версию сборки из `app\build.json`; файла нет — `build dev`.
- второй экземпляр блокируется mutex `Local\LegacyPlugExecutor`.

### `plug_control.py` — намерение и CLI

- режимы `auto`, `on`, `off`, `paused`; поле `until` — срок (`null` — до ручного
  возврата); запись атомарная (временный файл + `os.replace`).
- истёкший срок трактуется как `auto`; исполнитель один раз переписывает файл
  (`source: expiry`).
- CLI: `on|off|auto|resume|pause|status`, `--for 30m|1h|2h|eod|manual`.
- в поставке для других ПК используется как модуль трея; отдельного CLI-ярлыка нет.

### `tray_plug.py` — иконка

- меню: состояние лампы, режим, «Включить»/«Выключить» с подменю срока,
  «Автоматика по встречам», «Снять автоматику», «Открыть plug.log», «Выход».
- «Выход» — полное выключение лампы: через `stop.ps1` завершаются наблюдатель,
  исполнитель и сам трей, поэтому автоматика не продолжает работать без
  видимого интерфейса.
- иконка отражает фактическое состояние; если статус старше 30 с — «исполнитель
  не отвечает».
- картинки состояний — `app\scripts\meetings\icons\lamp-on.png` (жёлтая) и
  `lamp-off.png` (серая). Грузятся в PNG с альфой; в кадр берётся только корпус
  лампы (самая крупная связная фигура), а дуги Wi-Fi и ореол свечения
  отбрасываются: на 16–24 px они превращались в дымку и отнимали высоту, из-за
  чего иконка была заметно мельче соседних. Корпус обрезается по содержимому и
  вписывается в квадрат 64×64 с полем ~3 %. Если файла нет, лампа рисуется
  кодом, поэтому трей не падает. «Снята автоматика» — серая иконка с полосами
  паузы, «нет данных» — она же с прозрачностью 60 %.
- тема Windows читается из `AppsUseLightTheme` при каждом обновлении статуса.
  На тёмной теме тёмные цоколь и контур поднимаются по яркости (сильнее всего
  для самых тёмных пикселей), иначе цоколь сливался с панелью задач. Смена темы
  перерисовывает иконку без перезапуска трея.
- исходники иконок нарисованы без альфа-канала: включённая — на чёрном фоне со
  свечением, выключенная — на белом. Фон снимает `packaging\key_icon.py`:
  для чёрного свечение получает альфу по яркости с обратным умножением цвета,
  для белого цвет восстанавливается по обратной композиции над белым.
- не подключается к устройству; второй экземпляр блокируется mutex
  `Local\LegacyPlugTray`.
- зависимости: `pystray`, `Pillow`.

### `tuya_setup.py` — получение ключей и проверка

- однократно: Tuya IoT Platform → Access ID/Secret → `dev_id` и `local_key`
  → `secrets\tuya_plug.json`.
- значения не печатаются (маски), секрет вводится скрыто.
- на шаге мастера адрес ищется UDP-поиском по `dev_id`; `--address` важнее
  найденного, облачный IP используется только как резерв.
- `--diagnose` проверяет только облачные эндпоинты; связь с розеткой им не
  подтверждается.
- `--verify` проверяет настроенную розетку: поиск адреса → чтение DP →
  переключение → повторное чтение → возврат исходного состояния. Требует
  tinytuya; во время встречи отказывается работать без `--force`.
- после записи настроек проверка выполняется автоматически: для пользователя это
  один инструмент «настройка и проверка». Повторный запуск без `--reconfigure`
  тоже проверяет розетку, а `--reconfigure` перезаписывает ключи (замена или
  перепривязка устройства).

### `tuya_discovery.py` — поиск адреса

- активный скан `tinytuya.scanner.devices(...)` (пакет установлен — используем);
- резерв — пассивное прослушивание UDP 6666/6667/7000: устройства сами
  объявляют себя, разбор через `tinytuya.decrypt_udp`; нужен только стандартный
  Python;
- совпадение определяется по `gwId`/`id`, ключи не используются; найденный адрес
  подтверждается чтением статуса вызывающим кодом.

## 3. Файлы и каталоги (в поставке)

```
app\scripts\meetings\        скрипты и tuya_discovery.py
app\scripts\meetings\icons\  lamp-on.png, lamp-off.png для трея
app\build.json               версия, дата, commit (в репозитории нет — «dev»)
app\data\work\meetings\      state.json, control.json, plug_state.json, журналы
app\secrets\tuya_plug.json   dev_id, local_key, адрес, версия протокола, DP
```

Корень вычисляется как два уровня выше каталога скриптов — и в репозитории, и в
установке. Поэтому пути в коде не параметризованы.

## 4. Конфигурация устройства

`app\secrets\tuya_plug.json`:

```json
{
  "name": "on-air lamp",
  "dev_id": "…",
  "local_key": "…",
  "address": "192.168.1.42",
  "version": "3.3",
  "switch_dp": "1"
}
```

`version` — версия локального протокола (3.1…3.5), при неудаче подбирается
вручную: 3.3 → 3.4 → 3.5. `switch_dp` — номер DP переключателя, у розеток
обычно `1`.

## 5. Ограничения (проверенные)

- Классы и заголовки окон зависят от версий Толка, Zoom и Телемоста; они уже
  менялись (свёрнутое окно Zoom, настройки Телемоста). Обновление приложения
  может потребовать правки кода.
- Аудиопризнак встречи отключён намеренно; встреча, у которой все окна попали в
  служебные, не будет зафиксирована.
- Розетка и ПК должны быть в одной подсети; изоляция клиентов и гостевой Wi-Fi
  ломают локальный протокол.
- `local_key` хранится открытым текстом: это доступ к розетке в локальной сети,
  не учётная запись. Файл не попадает в Git, журналы и отчёты.
- Автоматических тестов нет: поведение проверялось на реальных встречах и в
  ручных сценариях (см. `docs\HISTORY.md`).
